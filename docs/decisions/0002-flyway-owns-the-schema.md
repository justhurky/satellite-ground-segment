# 2. Flyway owns the schema and Hibernate validates against it

Status: accepted

## Context

`ddl-auto=update` is convenient and silently wrong: the production schema becomes whatever the
entities happened to imply, constraints are missing, and nobody can review a change. For a system
where a bad row is a safety problem, the schema deserves to be reviewed like code.

## Decision

Flyway migrations are the only source of truth. Hibernate runs with `ddl-auto=validate`, so a
mapping that no longer matches a migration fails at start-up, and in the test suite that means it
fails in CI. The migrations carry what the mapping cannot express: check constraints for every enum
column, bounds on APIDs and sequence counters, a constraint that a contact window ends after it
starts, and that its uplinked bytes never exceed its budget.

The same migrations run on H2 in PostgreSQL compatibility mode for fast tests and on real PostgreSQL
in a Testcontainers test, so there is only one set of SQL to maintain and both paths are exercised.

## Consequences

Entity changes always come with a migration, which is the intended friction. Two details had to be
pinned for the two databases to agree: `Instant` maps to `timestamp with time zone` with Hibernate's
instant JDBC type set to `TIMESTAMP_UTC`, and identity columns are declared as
`generated by default as identity`, which both engines accept.
